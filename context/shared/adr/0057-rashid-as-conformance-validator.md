# ADR-0057: rashid as the Conformance Validator

## Status

Accepted. Supersedes [ADR-0011](0011-mvp-validation-framework.md),
[ADR-0048](0048-cli-as-spec-source.md), and
[ADR-0056](0056-hermetic-shipped-schema-validation.md).

## Context

portolan-cli shipped its own validator: a rule framework (ADR-0011) with 19
rules under a repo-local `RULE-XXXX` namespace, defined in `spec/schema/rules.yaml`
and enforced against a spec that lived in this repository (ADR-0048 made the CLI
the spec's source of truth, mirrored outward to portolan-spec). ADR-0056 added a
hermetic schema-validation layer over a vendored STAC 1.1.0 closure.

That arrangement inverted in mid-2026. The specification moved back to
[portolan-spec](https://github.com/portolan-sdi/portolan-spec) as the
human-owned source of truth (the CLI-to-spec sync workflow was deleted in #646),
and the validator was extracted along the import-linter seam tracked in #563
into [rashid](https://github.com/portolan-sdi/rashid), a standalone package
with its own release cycle. rashid implements the spec's requirements manifest
(115 `PORTO-*` requirements) as `PTL-*` rules, gated by a bidirectional
spec-coverage test, and validates in five passes: metadata, structural (STAC
1.1.0, offline against schemas shipped in its wheel), profile schema (offline,
bundled), data (asset bytes: checksums, sizes, format magic, COG and GeoParquet
storage rules), and live (HTTP range and CORS probes of the hosting server).

Keeping a second validator in the CLI meant two disjoint rule vocabularies, a
stale spec fork (this repo's `spec/` claimed version 0.1.1; upstream released
0.1.0), and rules that lagged the spec. The CLI's own output violated the
spec's conformance MUST — it never emitted the versioned profile schema URI.

## Decision

1. **rashid is the only validation engine.** `portolan check` calls
   `rashid.validate()`; `portolan_cli/validation/` is an adapter (pass
   selection, `RulesConfig` from `.portolan/config.yaml`, output shaping,
   remediation classification), not a rule engine. The native rules,
   `spec/`, the `RULE-XXXX` namespace, and the vendored STAC closure are
   deleted.
2. **Rule ids are rashid's `PTL-*`, shown verbatim.** No translation layer.
   The ids cite `PORTO-*` requirements and are documented in rashid's
   `docs/rules.md`.
3. **Default passes: metadata + structural + data.** All offline for local
   assets. `--live` is opt-in (it probes the published host; `check` prints a
   reminder when the catalog has a `publish.public_url`). The schema pass
   stays opt-in (`--schema`): rashid's parity gate proves
   `schema_invalid => hand-rule error`, so running it by default would report
   each defect twice — with a worse message and no fix hint — which is
   exactly the noise that breaks an agent's check → fix → re-check loop. It
   remains useful as a cross-check on catalogs produced by other tooling.
4. **Remediation lives in the CLI, keyed on rule id.** Every `PTL-*` id maps
   to a bucket: AUTO (mechanical edit, `check --fix` performs it), INSTRUCT
   (judgment needed; `check` emits an imperative requirement an agent or
   human satisfies iteratively), or EXTERNAL (server configuration; report
   only). Unmapped ids degrade to INSTRUCT, never crash.
5. **Spec ownership: portolan-spec.** Requirement changes land there first,
   paired with a rashid rule change (enforced by portolan-spec's
   companion-PR workflow), then whatever generation change the CLI needs so
   `tests/integration/test_generated_catalog_conformance.py` stays green.
6. **Version alignment.** The CLI pins a rashid version range in
   `pyproject.toml` and bumps deliberately; rashid pins the spec by commit
   (`SPEC_REF`) with a nightly drift canary. A nightly CI job here validates
   a freshly generated catalog against rashid `main`, so an upstream rule
   change surfaces before it ships.

## Consequences

- One vocabulary, one engine: a spec change cannot silently diverge between
  a local validator and the published one.
- Catalogs generated by older portolan-cli versions fail validation (they
  never carried the schema URI). Accepted pre-1.0; `check` detects the old
  generation markers (`portolan:version`, `portolan:geospatial`) and points
  at `check --fix`.
- Hermeticity (ADR-0056's goal) is preserved but relocated: rashid ships the
  STAC closure and the profile schema in its own wheel. The CLI's vendored
  copy and `scripts/refresh_stac_schemas.py` are deleted.
- The byte-level data pass runs on every `portolan check`, so `check` reads
  every asset. `--no-data` is the escape hatch for very large catalogs; an
  mtime/size cache is a tracked follow-up.
- The `extension_registry` ↔ `spec/extensions.md` parity gate died with
  `spec/`. Extension-vocabulary conformance is now rashid's concern
  (`PTL-AST`, `PTL-VIZ` media-type rules).
- Most remaining ADRs that restated spec content are now redundant; a
  follow-up issue tracks the purge.
